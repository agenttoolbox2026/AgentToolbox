# Approved creator updates: shared contract v1

Additive migration `0008_creator_updates.sql` extends the deployed 0007 contract. New direct owner instruction: approved external creators can submit updates to their tools. Intake remains open. No existing proposal, terms, entitlement, payment, ledger, purchase or review is changed.

## Stable identity and metadata versions

The original client-generated `atbc_` capability controls the same `platform_creators.creator_id` and approved `platform_creator_entitlements.tool_id`. No new credential, wallet proof, recovery grant or transferable identifier is introduced. Only approved original tools may submit updates. The original lifetime gross `share_bps=9000` entitlement remains immutable across all versions.

- `platform_creator_tool_versions`: `(tool_id TEXT, version TEXT) PK`, `approved_revision INTEGER`, `proposal_json TEXT`, nullable `source_submission_id TEXT FK`, nullable `source_update_id TEXT FK`, `approved_at TEXT`. Exactly one source is present. Append-only, unique `(tool_id, approved_revision)`. Initial approved proposal gets server-assigned metadata version `0.1.0`, revision 0. These are metadata approval versions, never proof of an installed endpoint/software version.
- `platform_creator_tool_heads`: `tool_id TEXT PK FK`, `current_version TEXT`, `revision INTEGER`, `updated_at TEXT`; composite FK to versions. One approved metadata head. Trigger-guarded updates only during an approved update decision. Existing approved initial proposals initialize their new metadata head from durable approval facts; this does not rewrite old records or backfill financial receipts.
- `platform_tool_update_proposals`: `update_id TEXT PK`, `tool_id TEXT FK`, `creator_id TEXT FK`, `base_version TEXT`, `expected_head_revision INTEGER`, `proposed_version TEXT`, `request_key_hash TEXT`, `request_hash TEXT`, `proposal_json TEXT`, `terms_json TEXT` (copy of original frozen terms), `state TEXT pending|approved|rejected`, `revision INTEGER` initially 0, `created_at TEXT`, `client_hash TEXT`. Unique `(tool_id, creator_id, request_key_hash)`. All fields except state/revision are immutable. Proposed version must be canonical bounded SemVer and greater than the current base at submission; no prerelease/build suffix in v1.
- `platform_tool_update_decisions`: `decision_id TEXT PK`, `update_id TEXT UNIQUE FK`, `reviewer_subject TEXT`, `request_key_hash TEXT`, `request_hash TEXT`, `expected_revision INTEGER`, `resulting_revision INTEGER`, `expected_head_revision INTEGER`, `decision TEXT approved|rejected`, `reason TEXT`, `created_at TEXT`. Unique `(reviewer_subject, request_key_hash)`, append-only. Same actor/hash/reason bounds as 0007.

## Private owner decision write

Owner API uses existing private authentication, same-origin JSON, session-bound CSRF, no-store and idempotent reviewer/key + matching request hash. INSERT exactly the decision fields above with `resulting_revision=expected_revision+1` and `expected_head_revision` from the immutable proposal. Do not independently update proposals/heads or insert versions.

The INSERT trigger atomically checks pending proposal + expected proposal revision. Approval also checks current head revision/base matches the immutable proposal. It inserts the new immutable metadata version, moves the head by one revision, and marks the proposal approved in one transaction. Competing approvals for the same base can approve at most one; stale approval raises `tool_head_conflict` and rolls back audit/version/head/state together. Rejection marks only that proposal and audit, even if its base has become stale. Pending/rejected proposals retain the previous approved head. No decision changes the original entitlement or installed adapter, and no URL/schema is fetched or executed. Approval of an update requires separate installed-adapter review before it changes paid execution.

## Public capability API/MCP

- `GET /v1/creator-tools/{tool_id}` + `X-Creator-Capability`: private current approved metadata/head revision, frozen entitlement terms and paginated approved history (`limit` 1–20, default 10; opaque bounded `cursor`). Wrong capability and unknown/unapproved tool both return 403.
- `POST /v1/creator-tools/{tool_id}/updates`: original capability header plus strict body `{request_id, creator_secret_hash, terms_version, base_version, expected_head_revision, proposed_version, proposal}`. `proposal` uses the same bounded private schema as initial submissions. `terms_version` must match the original frozen terms. Replay is scoped to the original creator + stable tool + request ID; identical replay is safe after head changes. Changed body with same scoped key conflicts.
- `GET /v1/tool-updates/{update_id}` + original capability: private proposal, state/revision and reviewer decision (reason/time only; no owner identity or hashes).
- MCP `get_creator_tool`, `submit_tool_update`, `get_tool_update` share those gates; capability is a private separate `creator_capability` argument, never a URL or proposal field.
- Human `/update-tool` form uses the original capability to read the approved head, then submit a separate versioned update for review. It does not create a new creator capability or request payment.

Updates share the original admission budget: combined initial proposals + updates at most 4/client/day, 40/day globally; shared write rate and 16 KiB body bound. Original-capability-in-proposal rejection, inert URLs/schemas and safe text rendering apply. No new update fee is collected; current zero-fee promotion remains explicit and no payout/refund transfers occur. Missing monetary facts remain unavailable; no invented approvals, refunds or earnings.

Production ordering: apply 0008 before either updated Worker. Preserve existing data and reconcile the prior approved heads and immutable financial facts afterward. Local synthetic fixtures only for positive tests.

## Outstanding quotes and operations

The metadata head is not the installed paid product version. Approving an update does not change the registry product/handler, installed adapter or beneficiary. Quotes continue to bind the installed product version, amount, input, requirements, minimum policy, and (for creator adapters) the server-only immutable installed adapter revision ID. A separately reviewed adapter change uses a new immutable `creatorAdapterId` and product version; an unclaimed quote for the old adapter fails closed (`quote_terms_changed` or `quote_mismatch`) before verification/execution/settlement. No quote silently rebinds to the latest metadata head. New first-party quotes retain their existing policy format.

An operation already admitted freezes installed product version, exact requirements, original creator/tool/share and the handler used by that request. Later metadata approval or adapter removal cannot rewrite that operation or its receipt/allocation. Durable settled replay returns its original retained result without verification/execution/settlement; pending/unknown operations require reconciliation without a replacement authorization. The update API never installs an adapter; future adapter installation must follow this immutable revision contract. Local mocked payment tests cover metadata approval with an outstanding quote, separately changed adapters, frozen receipts and replay. No live payment tests are used.
