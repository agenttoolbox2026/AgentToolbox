# Phase 1: learn from an external agent purchase

The first milestone is one verified paid purchase by an external agent. The four
current tools are experiments in agent value, discovery, trust and payment
friction. The purpose is learning that informs Phase 2. Creator submissions and
reviewed updates ship alongside this buyer experiment under Douglas's subsequent
instruction; they do not depend on the first paid purchase.

## Run the smallest useful observation

Start with an external agent's actual task that fits a published tool contract.
Record how it encountered the tool and what assistance it needed. Let it inspect
the outcome, price and free example or optional preview, then choose whether to
buy. The default direct price is $0.01 USDC; no separate quote is needed. Any
live-money authorization remains with the buyer or user. Do not obtain buyer
keys, sign on their behalf, transfer funds or spend money to manufacture a milestone.

Use existing private feedback and reports, plus a compact private experiment
record. No new dashboard is needed. Keep one row or short note for each observed
attempt; leave unavailable facts unknown. Record these questions separately:

| Question | Useful observation |
| --- | --- |
| Discovery | Where did the agent find the tool? Could it select the relevant contract without help? Record an assisted introduction as assisted. |
| Authorization | Could it understand the 402, obtain permission/funds and use its client? Record the exact non-sensitive blocker and stage. A missing wallet is not proof of weak tool value. |
| Clear outcome | Could it explain what success buys, when it would not be charged and what the result excludes? |
| Value | Did the result help its real task? Keep observed completion separate from its opinion. Record why it chose a paid call over its available alternative, if known. |
| Repeat | Did it independently return and pay for another useful task? Distinguish a new purchase from replay, a prompted trial and repeated use of a shared wallet. |

Do not send invitations or outreach without authorization. Discovery research,
clearer examples and draft materials can proceed without sending messages.
Do not store credentials, payment signatures, private capabilities, raw wallets
or sensitive task inputs in the experiment note. Reference access-controlled
execution evidence instead of copying private payloads.

## Verify the first milestone

Keep three facts distinct:

1. **Outcome:** a specific product/version operation passed its published charge
   checks and has a retained completion/receipt record. Caller-reported usefulness
   is separate evidence.
2. **Payment:** live settlement completed; independently confirm the matching
   Base USDC transaction and received amount. A facilitator report alone is not
   independent chain reconciliation. Unknown or pending settlement stays unresolved.
3. **External agent:** document the evidence that an external agent invoked the
   tool for an actual task and any founder intervention. A different payer wallet,
   capability possession, public review or counter increase alone cannot prove it.

Exclude founder/self-purchases (including other founder-controlled wallets),
controlled/synthetic tests, mocks, free examples, unsigned 402 probes, replays,
failed and unresolved payments from the milestone. Integration success and raw
traffic remain useful technical observations. They do not count as customers.
Do not relabel unclassified activity as organic demand or treat missing records
as a zero result. Preserve all underlying financial history.

A compact evidence record can contain the observation date, private operation
reference, product/version, outcome evidence reference, independently checked
transaction reference/amount, external-agent evidence reference, founder
assistance, discovery source, blockers, value feedback and next action. Mark
self-reports and unknowns explicitly; publish no private evidence by default.

## Decide what to change

After an observation, fix the most specific supported blocker and check the same
flow again. If discovery fails, improve the relevant discovery information. If
authorization fails, make the supported payment path clear. If the promised
outcome is unclear, improve that contract. If the result lacks value, revise or
retire that product based on evidence. Do not infer all four from a missing sale.

Use relevant comparisons to test value when needed; never invent token savings,
conversion rates, sample-size thresholds or customer claims. Fix observed buyer
blockers while shipping the authorized creator intake and update flow. Additional
tools, integrations and social features should address a demonstrated problem.
Continue observing return purchases without counting scripted repeats as retention.

The first verified external purchase clears the buyer milestone. It does not
establish repeat demand, validate future marketplace pricing or implement payout
splits. Review the evidence and remaining friction when choosing further scope.

## Observe creator supply separately

The parallel hypothesis is that external agents can supply useful tools, attract
buyers and reduce the need to build every tool ourselves. Record genuine
submissions, approval outcomes, update friction and any resulting buyer activity
without treating one as proof of another. A submission or approval is not a
purchase. The current $0.50 list fee is 100% discounted, so submissions currently
produce no fee revenue.

Approved creators can propose updates using the same private capability and
stable tool identity. Review changes, retain the last approved version until
acceptance, and never automatically execute arbitrary proposal code or URLs.
Treat update availability as a deployment fact to verify, not an assumed result.

Preserve accepted terms and the current approved creator entitlement to 90% of
lifetime gross revenue. Future marketplace fee hypotheses cannot rewrite those
commitments. Accrual is not a payout; nonzero charging and x402 split transfers
remain unimplemented. Use existing private records for learning without exposing
proposals or capabilities.
