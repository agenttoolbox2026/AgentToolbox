# Creator destination and payout contract

This document describes the original wallet and payout foundation (migrations 0011/0012). The subsequent [seller/referrer operator integration](payout-operator-contract.md) adds capability-owned payout requests, protected operator helpers, a fixed read-only RPC adapter, referral payouts and reviewed creator installation. Its additional migrations and deployment gates apply to the combined release.

This additive implementation preserves `creator-promo-2026-10-07.v1`, the original receiver, and every existing receipt, allocation and 90% lifetime gross entitlement. It collects a private payout address, verifies optional EOA ownership proof, and provides owner-only payout planning and independent receipt reconciliation. It contains no treasury key, signer, transfer broadcast, autonomous payout, or public payout-initiation endpoint.

Apply `0011_creator_wallets.sql` then `0012_creator_payouts.sql` before deploying this backend. Both are additive; there is no receipt backfill or historical rewrite. Parent audit and coordinated deployment are still required. All tests use local synthetic records. No production wallet, payout, or customer-purchase verification has been performed for this change.

## Public integration

All requests use the existing private `X-Creator-Capability`; MCP takes `creator_capability`. A previous submission must have created the capability-owned creator record. A submission ID, wallet address, transaction hash or signature by itself never grants creator access. Do not add these credentials to URLs or logs. Responses are `no-store`. The common 16 KiB body bound, service/client rate limits and shared write limiter apply. Wallet claim/challenge/proof writes additionally share a database-enforced 10-per-creator/day, 1000-global/day budget; identical replay does not consume another record.

| Route | Contract |
| --- | --- |
| `GET /v1/creators/me/payout-wallet` | Current wallet or null, and private revision history; `limit` 1–20 plus returned cursor. |
| `POST /v1/creators/me/payout-wallet` | `{request_id, expected_revision, network:"eip155:8453", address}`. Initial revision is zero. Exact canonical address/body/key replay returns the same claim. |
| `POST /v1/creators/me/payout-wallet/challenge` | `{request_id, claim_revision}` returns the exact five-minute ownership message. |
| `POST /v1/creators/me/payout-wallet/verify` | `{challenge_id, signature}` verifies that exact message. Identical saved proof replays; an unused expired challenge fails. |
| `GET /v1/creator-tools/{tool_id}/earnings` | Exact Base USDC gross, accrued, fractional carry, confirmed paid, reserved, available, and execution status. Original capability required. |

MCP names: `get_creator_payout_wallet`, `claim_creator_payout_wallet`, `create_creator_wallet_challenge`, `verify_creator_wallet`, `get_creator_earnings`. OpenAPI contains the same strict input and response schemas. Owner helpers below are deliberately absent from HTTP/MCP.

Collection does not require proof or approval and does not block proposal intake. A destination starts `ownership_status:unverified`. A single-use ERC-4361 message binds the configured HTTPS domain, Base chain 8453, creator scope, claim UUID/revision, address, action, nonce and expiry. Successful ERC-191 verification changes only the derived proof state to `eoa_signature_verified`; it does not prove human identity or authorize payment. This release explicitly supports EOA signatures only, not ERC-1271 contract-wallet proofs. Raw signatures and creator capabilities are never stored. Owner approval is a separate immutable record and requires a proof for the current claim. Changes require a new revision, proof and approval. Any unresolved payout freezes destination changes until it is either cancelled before authorization or independently confirmed.

Frontend sequencing: retain the existing creator capability/retry envelope, submit the tool, then submit the address through the separate strict wallet route using a retained request ID. Do not add a wallet field to the existing strict tool-proposal schema. Wallet proof may be completed later; never ask for a seed phrase/private key or a payment authorization as ownership proof.

## Data and exact accounting

Migration 0011 adds immutable wallet claims, five-minute challenges, consumed proof records and owner approvals. Claims use creator-scoped idempotency and revision CAS; proofs have a unique challenge; owner approvals bind one exact claim. Revision/expiry/budget guards are database enforced. Migration 0012 adds immutable payout batch identities, frozen per-tool payout reservations, candidate transaction identities/nonces, append-only transition events and independently verified chain evidence. Existing allocations remain the only accrual source.

For each stable entitlement on Base USDC, `gross` is the complete sum of immutable qualifying allocation amounts, checked against their receipts. JavaScript `BigInt` computes `accrued = floor(9*gross/10)` and `carry = (9*gross)%10`, so `10*accrued + carry = 9*gross`. Carry is cumulative across receipts and payout periods, never rounded per page. `available = accrued - confirmed_paid - reserved`. Denominations are not mixed. No gas, facilitator charge, refund inference or referral commission reduces creator accrual. No refund clawback exists; a future refund policy requires an explicit traceable ledger extension.

Reads inspect at most 5001 allocations and 5001 payout rows per tool and fail closed above 5000 rather than return partial balances. Individual atomic amounts respect uint256; cumulative totals use arbitrary-precision integers. This deliberate bounded implementation needs a separately audited checkpoint/index design before a tool exceeds that history. Accounting reads are conservative bounded observations, not a transactional reporting snapshot. Immutable allocations, a paid-count CAS guard at reservation insertion, and one unresolved reservation per entitlement prevent concurrent or stale balance reads from over-reserving.

## Protected owner workflow

The functions in `platform/src/creator-payouts.js` and `approveWallet` are internal. Their caller must first establish the existing owner authorization; passing a reviewer string is audit attribution, not authentication. They must be integrated into the protected owner workflow or a reviewed operator adapter before use. Never expose them through the public app.

1. `approveWallet({db,claimId,reviewer,requestId,now})` records separate owner approval of a currently proof-verified destination.
2. `proposePayoutBatch({db,reviewer,requestId,items:[{tool_id,amount_atomic}],sourceAddress,now})` reserves one positive amount per tool, at most 20 tools, atomically. `sourceAddress` is trusted owner configuration for the existing funded source, never a public client-selected override. It must differ from each destination. The batch freezes each destination revision, denomination, source, amount and checked accounting hash/count. Identical replay is safe; changed replay conflicts.
3. `authorizePayout({db,payoutId,reviewer,requestId,expectedRevision,now})` authorizes one reserved item after owner review. Each item is independent; a grouped batch does not claim atomic on-chain execution. `getPayoutManifest({db,payoutId,reviewer})` then returns immutable unsigned ordinary USDC `transfer(address,uint256)` calldata. The owner supplies Base gas from platform funds and signs externally after reviewing the exact amount/destination/source. Nothing in this backend signs or broadcasts.
4. `registerPayoutTransaction({...eventArgs,transactionHash,rpc})` independently reads the transaction and checks chain, source, token, calldata, amount and nonce. Replacements must use the same nonce and exact intent. At most 20 candidates are recorded. Provider unavailability, a missing hash or invalid evidence does not release funds. `markPayoutUnknown(eventArgs)` explicitly records uncertain external execution while preserving the reservation. Never resend blindly.
5. `reconcilePayout({...eventArgs,transactionHash,rpc})` performs read-only RPC verification. It requires successful receipt, native Base USDC, exact transfer input and unique matching log, expected sender/recipient/amount, registered nonce, canonical inclusion block and finalized chain view. The inclusion timestamp must be strictly later than owner authorization's integer second, conservatively rejecting earlier matching transfers. A chain log can satisfy only one logical payout. Evidence insertion and the `paid` event commit in one database batch; failure preserves the prior reservation. Exact idempotent retries recover a lost response.

`eventArgs` contains `{db,payoutId,reviewer,requestId,expectedRevision,now}`. `rpc(method,params)` must be a trusted server-configured read-only provider adapter returning decoded results. Request bodies must never supply its URL or implementation. The verifier calls only `eth_chainId`, `eth_getTransactionByHash`, `eth_getTransactionReceipt`, `eth_getBlockByNumber`; results/log counts are bounded. No private wallet keys or payment signatures are required.

States: `reserved` → `awaiting_owner` → `submitted`/`unknown` → `paid`. `cancelPayout(eventArgs)` is permitted only while `reserved`, before a transfer manifest is released. `unknown` and postauthorization failures retain reservations indefinitely for reconciliation. Reverted or dropped transactions are never marked paid and are not automatically released/retried. Same-nonce replacements can be registered; a different nonce or exhausted candidate bound needs an explicit future reconciliation procedure. Finalized-chain reorgs beyond the provider finality assumption need a separately audited corrective record; existing immutable paid evidence is never silently rewritten.

## Deployment and remaining owner actions

The staged backend does not install creator tools, connect the protected owner workflow, select/fund a wallet, or configure a trusted RPC adapter. Approved tools remain metadata-only until a separately reviewed installed adapter produces live successful receipts. Consequently wallet collection alone cannot promise seller income. Existing financial receipts are facilitator-confirmed; outgoing payout evidence is independently checked through the configured read-only RPC, with that provider's trust/finality boundary.

After parent audit, the lead must apply both migrations with aggregate-history/FK preservation readback, integrate the wallet intake UI, and deploy the AGI Worker. The protected owner reviewer must wire the internal approval/proposal/manifest/reconciliation helpers under existing authorization. Before any real payout, the owner must review the verified destination, source balance and Base gas, authorize the exact unsigned manifest, sign externally, and reconcile its transaction. No new account system, secret grant, treasury key, smart contract, automatic transfer or production fixture is part of this change.

## Protocol and fee evidence

The current server configuration uses PayAI, not Coinbase's facilitator. Standard x402 exact EVM requirements select a single `payTo`; this implementation retains that receiver and performs no speculative split-contract work. See the [x402 exact EVM specification](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_evm.md). Ownership messages follow [ERC-4361](https://eips.ethereum.org/EIPS/eip-4361) with the EOA-only limit stated above.

PayAI's [pricing documentation](https://docs.payai.network/x402/facilitators/pricing), checked 2026-10-07, describes a lifetime free allowance and subsequently cost-plus per-settlement fees, with the [live price table](https://facilitator.payai.network/pricing) authoritative. There is no assumption of free settlement forever or a verified account-specific allowance. At a 0.01-USDC tool price, the platform's 10% is only 0.001 USDC; fees can exceed that share outside the allowance. That operating shortfall is the platform's responsibility and must never be deducted from the promised creator share. Ordinary outgoing owner-signed transfers additionally require Base gas. No fee purchase, account change or transfer was performed during verification.
